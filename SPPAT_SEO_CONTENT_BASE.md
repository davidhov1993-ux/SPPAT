1.  # HOMEPAGE — CHECK CONTENT COMPLETENESS

Re-read ALL actual homepage content in the supplied Markdown files.

Verify that your current homepage composition uses all important approved
homepage content.

Current composition:

Hero → Services → Technical Proof → Final CTA

Do NOT add sections merely to make the homepage longer.

However, if meaningful approved homepage content was omitted, integrate it into
the composition properly.

The homepage should create a complete visual and commercial narrative:

introduction → understanding of Sppat → services → technical competence /
differentiation → trust / proof where supported → conversion

Use only content that actually exists.

Do not invent additional marketing copy, statistics, testimonials, guarantees or
business facts.

================================================== 2. KEEP PAGE FAMILIES

Do NOT make every page artificially unique.

The use of shared layouts for related page families is intentional and approved.

For example:

- Tegelwerk service pages may share a coherent service-page system.
- Specialisatie pages may share a coherent specialization system.
- Kennisbank articles should share a consistent editorial reading system.

Consistency is part of the design.

However, verify that each shared layout genuinely accommodates the actual
content of every page in that family.

Where the content genuinely requires a variation, specify that variation.

Do not introduce variation merely for visual novelty.

================================================== 3. IMPROVE CTA RHYTHM

The current specification relies too frequently on:

"Standard centered CTA block."

This risks making long pages feel mechanically templated.

Keep a consistent Sppat CTA design language, but create a small controlled CTA
system.

Define 2–3 exact CTA compositions maximum.

For example, different compositions may be appropriate for:

- major commercial pages;
- technical/service pages;
- editorial/Kennisbank pages.

They must clearly belong to the same design system.

Specify exactly which CTA composition is used by which page/page family.

Do not create arbitrary variations.

================================================== 4. STRUCTURAL BORDERS — USE WITH DISCIPLINE

The architectural 1px gridline language is approved.

Keep it.

But review the instruction to use borders "extensively."

The website must not become visually boxed-in or resemble a spreadsheet.

Define clear rules for when structural lines are used and when whitespace alone
separates content.

Borders should reveal structure, not decorate every container.

Preserve the architectural precision while allowing large areas of visual calm.

================================================== 5. SPACING RHYTHM

Do not use 120px section padding mechanically across the entire website.

Create a controlled spacing scale appropriate for the design.

Define exact spacing tokens for:

- compact internal spacing;
- standard section spacing;
- major section transitions;
- hero spacing;
- CTA spacing;
- editorial/article spacing;
- mobile equivalents.

Then define when each level is used.

The objective is controlled visual rhythm, not random spacing and not identical
spacing everywhere.

================================================== 6. PROJECTEN — DO NOT INVENT PORTFOLIO DATA

Review /projecten/ against the actual supplied content.

Do NOT require:

- project filters;
- project titles;
- project locations;
- project tags;
- project categories;
- metadata;

unless those data actually exist in the supplied content.

If the available portfolio content is currently limited, design the page so it
still looks intentional and premium with limited real material.

Do not create functionality that requires nonexistent content.

If filters are genuinely supported by the source content, they must follow the
established sharp architectural design language — NOT pill-shaped controls.

================================================== 7. CONTACT — MISSING BUSINESS INFORMATION

Do not assume that Phone, Email, Address, KVK, BTW or other business details
exist unless explicitly supplied.

Design the Contact page so it remains visually complete without unresolved
business information.

If actual contact information exists in the supplied content, use it.

If it does not exist, do not invent it and do not create fake placeholders.

The form itself should remain the primary conversion mechanism.

================================================== 8. PRIVACY

Do NOT invent a /privacyverklaring/ page.

Do NOT instruct the developer to publish a "Content pending" page.

If the approved form content references privacy but no privacy-policy content or
route has been supplied, identify this as unresolved content for later
completion.

Do not solve it by inventing public website content.

================================================== 9. VISUAL AUTHENTICITY

Review every visual requirement.

Do not describe an image as:

- a Sppat project;
- a project completed in Almere;
- the Sppat founder;
- the Sppat team;
- a specific completed installation;

unless the supplied content/assets support that claim.

The visual specification may describe the desired subject and composition
without making unsupported factual claims.

For example:

Instead of: "Modern completed Sppat project in Almere"

Use: "Modern finished bathroom interior suitable for the composition; no
geographic or authorship claim."

Actual Sppat project photography will be distinguished from
illustrative/inspirational imagery later.

================================================== 10. MEDIA PLACEHOLDERS

Do NOT instruct the frontend developer to search Unsplash, stock libraries or
other sources.

Asset sourcing is a separate task.

The design specification should define the required media slot and exact art
direction.

Until final assets are supplied, the implementation must be capable of rendering
an intentional neutral placeholder or omitting the media without breaking the
layout.

================================================== 11. RESPONSIVE LOGIC

Resolve the current universal mobile ordering rules.

Do not establish contradictory rules such as:

"Image first, text second" and "Heroes use text first, image second."

Instead define responsive transformation according to component/page family.

Specify the intended order for:

- Home Hero;
- split service heroes;
- technical proof sections;
- service timelines;
- Specialisatie pages;
- Kennisbank;
- Contact;
- CTA components.

Mobile must feel deliberately designed rather than mechanically stacked.

================================================== 12. FINAL DESIGN COHERENCE CHECK

Review the entire website as ONE visual experience.

Check for excessive repetition of:

- centered blocks;
- bordered boxes;
- identical section heights;
- identical image ratios;
- identical CTA compositions;
- 50/50 splits;
- card grids;
- large empty spacing;
- terracotta accents.

Also check the opposite problem:

Do not introduce unnecessary variation just to make pages different.

The final website should balance:

SYSTEM + RHYTHM + VARIATION + CONSISTENCY.
